# 十二个核心用例

以下用例规格保留原设计语义。

## UC-01 用户认证

参与者：所有用户。

前置：账号存在且系统可用。

1. 输入用户名或邮箱及密码。
2. 系统验证凭证、启用状态及实际角色。
3. 创建会话并显示需求列表；退出时使会话失效。

异常：错误凭证拒绝；禁用账号拒绝；无权限资源请求被服务端拒绝。

后置：成功建立有效会话；失败时无新会话。

## UC-02 管理用户与角色

参与者：Administrator。

前置：已认证且具有 ADMIN。

1. 创建用户时提供 username、email、displayName、initialPassword 及至少一个预定义角色 roles；修改已有用户时读取其基本资料。
2. 服务端验证账号唯一及角色有效性，仅以请求输入接收 initialPassword，用 BCrypt 生成非空 passwordHash；数据库不保存明文，哈希永不返回客户端。
3. 在同一事务中保存用户及角色分配，grantedBy 取当前 ADMIN 的可信 userId；日志、AuditEvent 和响应均排除明文密码。
4. 正常资料修改或启用/禁用按权限执行，保存修订及审计；资料修改不更改 passwordHash。

异常：缺失初始密码或角色被拒；重复用户名/邮箱为冲突；非法角色或撤销最后角色被拒；修订冲突需重读。bootstrap 仅由受信任 migration 初始化，不调用本用例。

后置：新用户可以凭初始密码登录；数据库只有 BCrypt 哈希；响应无密码或哈希；合法资料与角色更新，历史引用保留。

## UC-03 创建与维护需求

参与者：Requirement Engineer。

前置：已认证且具有内容维护权限。

1. 填写草稿正式内容，系统生成编号及创建信息。
2. 编辑 DRAFT，逐步补齐来源、理由和验收标准。
3. 独立维护负责人和标签，保存修订及审计。

异常：非 DRAFT 禁止直接编辑；无效负责人拒绝；仅从未评审且无关系的草稿可逻辑撤销。

后置：创建或更新草稿；管理信息不生成正式版本。

## UC-04 推进需求生命周期

参与者：Requirement Engineer / Project Member。

前置：需求存在、未撤销；执行者具有该动作角色。

1. 工程师提交完整草稿或重新打开 REJECTED。
2. 项目成员针对当前正式版本确认实现。
3. 在 IMPLEMENTED 状态确认验证，保存说明及版本上下文。

异常：不完整提交失败；跳跃状态、错误版本或修订冲突拒绝。审批决策由 UC-05 完成。

后置：合法新状态及审计；提交时建立新的 PENDING 评审轮次。

## UC-05 评审需求

参与者：Reviewer。

前置：需求 UNDER_REVIEW，轮次 PENDING；评审者不是创建者。

1. 读取该轮提交快照及相关追踪信息。
2. 选择 APPROVE、REJECT 或 REQUEST_CHANGES，必要时填写意见。
3. 完成轮次；批准原子产生 V1，拒绝置 REJECTED，退回置 DRAFT。

异常：自我评审、意见缺失、已决策或需求状态变化均拒绝；事务失败回滚。

后置：评审记录不可变；首次批准形成唯一 V1。

## UC-06 查询与追踪需求

参与者：所有授权用户。

前置：具有需求查看权限。

1. 按关键词及状态、性质、层级、优先级、标签组合筛选并分页。
2. 打开需求详情，查看正式内容或未批准工作内容。
3. 读取当前入向/出向关系及版本、评审、变更、评论和历史入口。

异常：空结果正常；撤销需求默认不显示；追踪遍历设深度和 visited。

后置：获得符合条件的可见需求及追踪信息；不改变状态或版本。

## UC-07 管理需求关系

参与者：Requirement Engineer。

前置：两端需求存在且未撤销。

1. 选择源需求、目标需求、关系类型和说明。
2. 串行化写入；检查自关联、重复、对称规范化及依赖环。
3. 保存或解除关系并写审计，保留两端需求。

异常：自关联、反向对称重复及依赖环拒绝；关系不存在或已解除时返回冲突/不存在。

后置：当前关系更新；需求正式内容和版本不变。

## UC-08 查看需求版本与历史

参与者：所有授权用户，包括 Administrator。

前置：需求存在且有查看权限。

1. 查看正式版本列表及当前指针。
2. 读取指定版本的完整内容、产生者、时间、原因和唯一来源。
3. 读取需求业务审计、两类评审及变更历史。

异常：首次批准前说明没有正式基线；不存在版本拒绝；不提供历史修改动作。

后置：只读取得版本与业务证据；FR-AUDIT-004 在此覆盖。

## UC-09 协作与评论需求

参与者：Requirement Engineer / Reviewer / Project Member。

前置：已认证且有评论权限，需求未撤销。

1. 填写非空评论，系统记录作者和时间。
2. 授权用户查看评论；删除标记代替已删除正文。
3. 作者可逻辑删除本人评论，保存删除信息及审计。

异常：Viewer 不可发表；非作者不可删除；空正文拒绝。

后置：评论保存或逻辑删除；需求内容、生命周期和版本不变。

## UC-10 创建与管理变更请求

参与者：Requirement Engineer。

前置：目标已有基线且为 APPROVED/IMPLEMENTED/VERIFIED，无活动变更。

1. 创建 CR 时服务端复制目标当前基准版本及八项内容。
2. 填写申请标题、理由和建议内容，仅 DRAFT 可编辑。
3. 每次提交时锁定并检查对应 ChangeRequest，从该 CR 本身逐值复制 baseVersionId、requestTitle、reason 和全部 proposed 字段到本轮 snapshot 字段；复制与置 UNDER_REVIEW 在同一事务完成，快照创建后不可变；提出者也可取消草稿。

异常：无基线或已有活动变更拒绝；不完整提交失败；提交后的内容不得编辑。

后置：草稿、已提交或 CANCELLED 变更保留，当前需求仍不改变。

## UC-11 评审变更请求

参与者：Reviewer。

前置：变更 UNDER_REVIEW、轮次 PENDING；评审者不是提出者。

1. 读取本轮不可变的基准、申请标题、理由及八项建议快照；这些值由 UC-10 从对应 CR 的提交瞬间逐值复制。
2. 选择批准、拒绝或要求修改；拒绝和退回必填意见。
3. 完成轮次并置 APPROVED、REJECTED 或 DRAFT，旧快照保留；退回重提产生与新提交内容一致的新快照。

异常：自我评审、缺意见、重复决策或修订冲突拒绝。退回后由 UC-10 修改和重提。

后置：保存不可变评审；批准不创建正式版本；拒绝为终态。

## UC-12 应用批准的变更

参与者：Requirement Engineer。

前置：变更 APPROVED；基准属于本需求且仍是当前版本；修订号一致。

1. 锁定需求与变更，复核状态、版本和一次性执行条件。
2. 插入 V(n+1)，复制已批准内容到需求并更新指针及 APPROVED 状态。
3. 置 APPLIED，记录应用者和时间，与成功审计一同提交。

异常：非批准、过期或跨需求基准、重复应用、权限及修订冲突均拒绝；任一步失败全回滚。

后置：产生唯一新版本；新版本重新实现和验证；旧版本证据保留。
